1. Install the runner node

The runner node is one Docker container you host inside your network — it needs to reach the apps you monitor; the Checkmk server only needs to reach the node. Browsers (Chromium) ship pre-installed in the image.

git clone https://github.com/GranusClarvis/SynthMK.git && cd SynthMK
docker build -f runner-node/Dockerfile -t synthmk-runner .

docker run -d --name synthmk-runner --restart unless-stopped \
  -p 6556:6556 -p 9180:9180 -p 9181:9181 \
  --memory 6g --cpus 4 --shm-size 1g --security-opt no-new-privileges \
  -v "$PWD/flows:/opt/synthmk/flows" \
  -v "$PWD/runner-node/flows.conf:/opt/synthmk/runner-node/flows.conf" \
  -v "$PWD/secrets.yaml:/run/synthmk/secrets.yaml:ro" \
  -e SYNTHMK_SECRETS_FILE=/run/synthmk/secrets.yaml \
  -e SYNTHMK_SHOT_BASE_URL="http://<node-lan-ip>:9180" \
  synthmk-runner
Set SYNTHMK_SHOT_BASE_URL to an address other machines can reach (the node's LAN IP or DNS name) — that's the URL screenshot links in Checkmk will point at. localhost only works on the node itself.

Port contract: 6556 agent transport (firewall: Checkmk server only) · 9180 screenshots (token-auth) · 9181 management dashboard (token sign-in). A production compose.yaml with limits and named volumes ships in runner-node/.

2. Install the Checkmk plugin

Download synthmk.mkp and install it on your site — GUI (Setup → Maintenance → Extension packages → Upload) or CLI:

mkp add synthmk.mkp
mkp enable synthmk $(mkp list | awk '$1=="synthmk"{print $2}')

This installs the native check plugin (services + per-step metrics), the Setup ruleset, and the graph definitions. Checkmk Raw 2.3+ — no enterprise edition required.

3. Add the node to Checkmk

  1. Setup → Hosts → Add host — hostname/IP of the runner node, monitored via Checkmk agent (it answers on TCP 6556).
  2. Save & run service discovery. Every configured flow appears immediately (the node publishes warm-up placeholders under the real service names), plus a SynthMK Scheduler health service.
  3. Activate changes. Done — synthetic services with graphs and thresholds.

Per-site attribution (piggyback): give a flow a checkmk_host and the result is attributed to that host instead — one node, every monitored app appearing as its own Checkmk host. Create those hosts with No API integrations, no Checkmk agent.

4. Record a check

  1. Install the extension (Chrome/Edge: load unpacked via developer mode; Firefox: temporary add-on).
  2. Open your app, click the SynthMK icon, hit ● Start.
  3. Do the journey once, like a user. Watch steps appear live in the popup — delete mis-clicks with ✕.
  4. Add at least one assertion (Visible text / Title contains / URL contains).
  5. Name the check, set WARN/CRIT thresholds, Download .yaml.
  6. Add it to the node: paste into the dashboard editor (lints before saving) or drop the file in flows/ + one line in flows.conf: 
    my-login.yaml   300   shop-frontend   # file  interval_s  [checkmk_host]

5. Secrets & login flows

When you type into a password field while recording, the exported step is:

- action: fill
  selector: "#password"
  value: "{{ secret.password }}"
  sensitive: true

The real value goes in a YAML secrets file on the node, never in the flow:

# secrets.yaml — chmod 600, mounted read-only into the container
password: the-real-password
portal_user: monitor-bot

The runner refuses secrets files readable by group/world, fails UNKNOWN on missing names (never runs with blank credentials), redacts every secret value from service output, and blanks form fields before failure screenshots when a sensitive fill ran.

6. The node dashboard

http://<node>:9181 — sign in with the admin token (SYNTHMK_ADMIN_TOKEN, or auto-generated and printed once in the container log). You get live states with per-step timings, Run now, failure screenshot links, and a flow editor that runs the linter before every save — invalid YAML never lands on disk. Mount flows/ read-only if you want a view-only dashboard.

7. Settings in Checkmk

Setup → Service monitoring rules → SynthMK synthetic browser checks — override journey duration thresholds per service (or per host/folder/label like any Checkmk rule) without touching the node. The flow file's warn_ms/crit_ms apply when no rule matches.

8. Failure screenshots

Flows with screenshot_on_failure: true capture the page at the failing step. Links carry a per-file HMAC token (no listing, no traversal, 403 without the token). To make them clickable in the Checkmk GUI, set "Escape HTML codes in service output" = Do not escape scoped to the SynthMK hosts only (escaping-off is an XSS surface; SynthMK emits a single sanitized line).

9. Scaling

The scheduler runs flows into the Checkmk spool dir, so agent polls are always instant; a worker pool (SYNTHMK_MAX_CONCURRENCY, default 4) bounds concurrent browsers. Capacity rule of thumb:

avg_concurrency = runs_per_minute × avg_flow_seconds / 60   # keep < pool/2

Measured: 60 flows at 1–3 min intervals ≈ 37 runs/min sustained on one default node, zero overdue. If you oversubscribe, the SynthMK Scheduler service WARNs on the node — monitored apps never show false CRITs. Details: docs/scaling.md.

10. TLS transport (production)

The default transport is plaintext TCP 6556 (firewall it to the Checkmk server). For TLS, register the official agent controller — one command:

docker exec -e CMK_PASSWORD=... synthmk-runner \
  bash /opt/synthmk/runner-node/register_agent.sh \
  --server cmk.example.lan:8000 --site mysite --user automation --host synthmk-runner
# then restart with SYNTHMK_AGENT_MODE=official

FAQ

Does it work on Checkmk Raw?

Yes — that's the point. Raw 2.3 is the verified target. No enterprise features required.

Can I monitor sites behind a login?

Yes — that's the flagship use case. See secrets; the lab ships a full login → dashboard example journey.

Can I check Google / public sites?

Public search engines bot-block headless datacenter traffic (we verified — reCAPTCHA on Google, duck-CAPTCHA on DuckDuckGo). Wikipedia works; your own apps are the intended target. A consent-click Google template ships as the journey shape.

How is this different from Robotmk?

See the comparison: free edition support, Playwright + YAML instead of Robot Framework, a pre-baked container instead of RCC env builds, recorded flows instead of hand-written suites, and a stricter credential story.

Where do I report issues?

GitHub Issues. The full test evidence per release lives in docs/STATUS.md.
