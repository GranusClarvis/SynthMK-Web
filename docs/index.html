Install the runner node

The runner node is one Docker container you host inside your network. It needs to reach the apps you monitor; the Checkmk server only needs to reach the node. Browsers ship pre-installed in the image.

git clone https://github.com/GranusClarvis/SynthMK.git && cd SynthMK
docker build -f runner-node/Dockerfile -t synthmk-runner .

docker run -d --name synthmk-runner --restart unless-stopped \
  -p 6556:6556 -p 9180:9180 -p 9181:9181 \
  --memory 6g --cpus 4 --shm-size 1g --security-opt no-new-privileges \
  -v "$PWD/flows:/opt/synthmk/flows" \
  -v "$PWD/runner-node/flows.conf:/opt/synthmk/runner-node/flows.conf" \
  -v "$PWD/secrets.yaml:/run/synthmk/secrets.yaml:ro" \
  -e SYNTHMK_SECRETS_FILE=/run/synthmk/secrets.yaml \
  -e SYNTHMK_SHOT_BASE_URL="http://<node-lan-ip>:9180" \
  synthmk-runner
Set SYNTHMK_SHOT_BASE_URL to an address other machines can reach (the node's LAN IP or DNS name). That is the URL screenshot links in Checkmk will point at. localhost only works on the node itself.

Port contract: 6556 agent transport (firewall: Checkmk server only) · 9180 screenshots (per-file token auth) · 9181 management dashboard (token sign-in). A production compose.yaml with limits and named volumes ships in runner-node/.

Install the Checkmk plugin

Download synthmk.mkp and install it on your site, via the GUI (Setup → Maintenance → Extension packages → Upload) or the CLI:

mkp add synthmk.mkp
mkp enable synthmk $(mkp list | awk '$1=="synthmk"{print $2}')

This installs the native check plugin (services + per-step metrics), the Setup ruleset, and the graph definitions. Checkmk Raw 2.3+; no commercial edition required.

Add the node to Checkmk

  1. Setup → Hosts → Add host: hostname/IP of the runner node, monitored via Checkmk agent (it answers on TCP 6556).
  2. Save & run service discovery. Every configured flow appears immediately (the node publishes warm-up placeholders under the real service names), plus a SynthMK Scheduler health service.
  3. Activate changes. Done: synthetic services with graphs and thresholds.

Per-app attribution (piggyback): give a flow a checkmk_host and the result is attributed to that host instead: one node, every monitored app appearing as its own Checkmk host. Create those hosts with No API integrations, no Checkmk agent.

Record with the extension

  1. Install the extension (Chrome/Edge: load unpacked via developer mode; Firefox: temporary add-on).
  2. Open your app, click the SynthMK icon, press Start.
  3. Do the journey once, like a user. Steps appear live in the popup; delete mis-clicks directly in the list.
  4. Add at least one assertion (Visible text / Title contains / URL contains) so the flow asserts an outcome.
  5. Name the check, set WARN/CRIT thresholds, Download .yaml.
  6. Add it to the node: paste into the dashboard editor (lints before saving), or drop the file in flows/ plus one line in flows.conf: 
    my-login.yaml   300   shop-frontend   # file  interval_s  [checkmk_host]

Password fields are recorded as {{ secret.* }} references automatically. The typed value never enters the extension. See Secrets.

Import from Chrome DevTools Recorder

No extension required: every Chrome ships a recorder. To author from any desktop, including locked-down ones:

  1. In Chrome: DevTools (F12) → Recorder panel → Create a new recording. Record the journey, stop.
  2. Export the recording as JSON (the Recorder panel's export menu).
  3. On the node dashboard, choose Import recording and upload the JSON. SynthMK converts the steps and selectors into a normal YAML flow and opens it in the editor.
  4. Review, add assertions and thresholds, save. The importer output is linted like any other flow.

DevTools recordings include several selector candidates per step (CSS, ARIA, text). The importer keeps them as a selector fallback array, so imported checks start out resilient to frontend refactors.

The visual step builder

The dashboard's step builder authors a check without recording or writing YAML:

  1. In the dashboard, choose New check → Build visually and enter the start URL. The node opens a live preview of the page.
  2. Click an element in the preview, then pick the action: click, enter text, enter login/password (picks a name from the secrets store; the value is never shown), select dropdown option, or an assertion (text visible, text absent, element attribute, checkbox state).
  3. Repeat until the journey is complete; reorder or delete steps in the side list.
  4. Set name, interval and thresholds, then save. The builder writes ordinary flow YAML. You can switch to the YAML view at any time, and the linter gates the save.

Because the builder selects elements on the live page, it records selector fallback arrays the same way the DevTools importer does.

Secrets, logins & TOTP

When you type into a password field while recording (or pick “enter password” in the step builder), the step that lands in the flow is:

- action: fill
  selector: "#password"
  value: "{{ secret.password }}"
  sensitive: true

The real value goes in a YAML secrets file on the node, never in the flow:

# secrets.yaml: chmod 600, mounted read-only into the container
password: the-real-password
portal_user: monitor-bot
vpn_totp: "JBSWY3DPEHPK3PXP"   # base32 TOTP seed

Guarantees enforced by the runner:

  • A secrets file readable by group/world (or owned by the wrong user) is refused at startup; the check goes UNKNOWN with a “chmod 600” message instead of running insecurely.
  • A missing secret name fails UNKNOWN, so the flow never runs with blank credentials.
  • Every resolved value is redacted to *** in service output, errors, logs and spool files.
  • After a sensitive fill, form fields are blanked before any screenshot.

TOTP / MFA: {{ totp.vpn_totp }} generates a current RFC 6238 code (6 digits, 30-second period, the standard authenticator format) from the base32 seed stored under that name in the secrets file. Use it to monitor MFA-enforced logins without weakening the account.

Also available: {{ var.uuid }}, {{ var.timestamp }} and {{ var.random }}: per-run values that stay stable within a run, so you can type a unique address and assert the page echoes it back.

Reusable sub-flows

Repeated step sequences, almost always the login, can be defined once and included from any flow:

# flows/shared/login.yaml is a fragment: only its steps are used
name: shared portal login (fragment)
steps:
  - action: open_url
    url: "https://portal.example.lan/login"
  - action: fill
    selector: "#username"
    value: "{{ secret.portal_user }}"
    sensitive: true
  - action: fill
    selector: "#password"
    value: "{{ secret.portal_password }}"
    sensitive: true
  - action: press
    key: "Enter"

# any flow that needs a logged-in session:
steps:
  - action: include
    flow: shared/login.yaml
  - action: check_visible_text
    text: "Dashboard"

Sub-flow steps are inlined when the flow loads (cycle-safe, max 3 levels), so per-step timings still show each real step, and a broken login shows the failing step's own name. The linter follows includes and lints the target.

Playwright script checks (trust-gated)

For journeys that genuinely need code, the node can run Playwright Python scripts as checks: same scheduler, same output contract, same screenshot and redaction behavior.

This is disabled by default, by design. Operator-supplied code on a monitoring probe is remote code execution; SynthMK treats enabling it as an explicit operational decision:

  • The node must set SYNTHMK_ALLOW_SCRIPTS=1 in its environment. Without it, every type: script flow reports UNKNOWN and no script ever executes.
  • Scripts cannot be created or edited from the dashboard. They arrive via the mounted flows directory only, so your existing code-review path applies.
  • Script runs are bounded by the same hard timeout and worker pool as YAML flows, and appear in the audit log like any other check activity.

The flow file says type: script and script: scripts/x.py (relative path); the script defines run(page, api): page is the raw Playwright page, api adds api.step("label") timings, api.secret() / api.totp() (auto-redacted), api.screenshot() and api.fail(). See flows/scripts/example_journey.py for the full contract.

The node dashboard

http://<node>:9181. Sign in with the admin token (SYNTHMK_ADMIN_TOKEN, or auto-generated and printed once in the container log). You get live states with per-step timings, Run now, failure screenshot links, the step builder, the recording importer, and a flow editor that runs the linter before every save, so invalid YAML never lands on disk. Mount flows/ read-only for a view-only dashboard.

Pause, tags, history, audit

  • Pause / resume: stop a check during a maintenance window without deleting it; paused checks are visibly marked and excluded from scheduling until resumed.
  • Tags: label checks by team or application and filter the dashboard by tag.
  • Version history: every flow edit made through the dashboard is kept as a revision; compare and roll back to a previous version in one click.
  • Audit log: flow edits, pauses, run-now triggers and imports are recorded with timestamp and acting session, viewable in the dashboard.

Thresholds in Checkmk Setup

Setup → Service monitoring rules → SynthMK synthetic browser checks: override journey duration thresholds per service (or per host/folder/label like any Checkmk rule) without touching the node. The flow file's warn_ms/crit_ms apply when no rule matches.

Failure screenshots

Flows with screenshot_on_failure: true capture the page at the failing step (an always-on screenshot step exists too, for evidence captures). Links carry a per-file HMAC token: no listing, no traversal, 403 without the token. To make them clickable in the Checkmk GUI, set “Escape HTML codes in service output” = Do not escape, scoped to the SynthMK hosts only (escaping-off is an XSS surface; SynthMK emits a single sanitized line).

Scaling

The scheduler runs flows into the Checkmk spool dir, so agent polls are always instant; a worker pool (SYNTHMK_MAX_CONCURRENCY, default 4) bounds concurrent browsers. Capacity rule of thumb:

avg_concurrency = runs_per_minute × avg_flow_seconds / 60   # keep < pool/2

Measured: 60 flows at 1 to 3 minute intervals ≈ 37 runs/min sustained on one default node, zero overdue, agent poll under 0.5 s. If you oversubscribe, the SynthMK Scheduler service WARNs on the node, and monitored apps never show false CRITs. Method and worked examples: docs/scaling.md.

TLS transport (production)

The default transport is plaintext TCP 6556 (firewall it to the Checkmk server). For TLS, register the official agent controller with one command:

docker exec -e CMK_PASSWORD=... synthmk-runner \
  bash /opt/synthmk/runner-node/register_agent.sh \
  --server cmk.example.lan:8000 --site mysite --user automation --host synthmk-runner
# then restart with SYNTHMK_AGENT_MODE=official

The agent can also be baked into the image at build time (--build-arg CMK_AGENT_DEB=<site agent .deb url>) so production nodes carry the TLS controller with zero runtime download; registration remains a one-time runtime step. Keep a volume on /var/lib/cmk-agent so the registration survives container recreation.

FAQ

Does it work on Checkmk Raw?

Yes, that is the point. Raw 2.3 is the verified target. No commercial edition or add-on subscription required.

Can I monitor sites behind a login?

Yes, that is the flagship use case, including MFA accounts via TOTP secrets. The lab ships a full login-to-dashboard example journey.

Can I check Google / public sites?

Public search engines bot-block headless datacenter traffic (verified: reCAPTCHA on Google, equivalent on DuckDuckGo). Wikipedia works; your own apps are the intended target.

How is this different from Robotmk?

See the full comparison: free-edition support, Playwright + YAML instead of Robot Framework, a pre-baked container instead of RCC environment builds, four authoring paths, and a stricter credential story.

Where do I report issues?

GitHub Issues. Per-release test evidence lives in docs/STATUS.md.
