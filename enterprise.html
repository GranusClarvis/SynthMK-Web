Security & operations

A synthetic monitor holds your passwords and watches your internal apps

SynthMK is designed around that fact. This page is the full model — what the product enforces, what was actually tested, and what remains your responsibility as the operator. The per-release test evidence behind every claim is public in docs/STATUS.md.

Credentials

Secrets are referenced, never embedded

Flow files contain {{ secret.name }} references. The values live in one YAML file on the runner node and nowhere else — not in flows, not in git, not in the Checkmk configuration, not in the recorder.

  • Permission-enforced at startup. The runner refuses a secrets file that is group- or world-readable, or owned by the wrong user — it fails UNKNOWN with a clear message instead of running insecurely.
  • Hard redaction everywhere. Every value resolved from the secrets file is scrubbed from service summaries, error messages, logs and spool files. A selector error that quotes the page can never quote a credential.
  • Masked before screenshots. When a sensitive fill ran, form fields are blanked before any failure or evidence screenshot is captured — verified by inspecting the actual PNGs.
  • TOTP for MFA logins. {{ totp.name }} generates RFC 6238 codes from a base32 seed stored in the same protected file — monitor MFA-enforced accounts without disabling MFA for them.
  • The recorder never sees a password. Typing into a password field records a reference and a sensitive flag; the typed value never enters the extension's state.
# secrets.yaml — chmod 600, mounted read-only into the node.
# This file is the ONLY place values exist.
portal_user: monitor-bot
portal_password: "…"
vpn_totp: "JBSWY3DPEHPK3PXP"   # base32 seed for {{ totp.vpn_totp }}

# What Checkmk sees when a login step fails:
CRIT - step 4 (fill #password): timeout — value '***' redacted

# What the flow file contains (safe to commit):
- action: fill
  selector: "#password"
  value: "{{ secret.portal_password }}"
  sensitive: true
Network surface

Three ports, each authenticated or scoped

The node exposes exactly three services, and the defaults assume a hostile LAN rather than a trusted one:

  • :6556 — agent transport. Production mode registers the official Checkmk agent controller in one command: certificate-based TLS, pull-only, paired to your site's CA. Verified live with cmk -d over TLS against Checkmk Raw 2.3. The plaintext fallback exists for labs and is labelled as such.
  • :9180 — screenshot server. Every screenshot URL carries a per-file HMAC token. No directory listing, no path traversal, 403 without the token, 404 for anything that is not a screenshot — each behavior is an explicit test case.
  • :9181 — management dashboard. Token sign-in with CSRF protection and constant-time comparisons; unauthenticated requests get 401, state-changing requests without the CSRF header get 401. Mount the flows directory read-only and it degrades to a view-only dashboard.
Runtime

A container that assumes it will be attacked

The shipped production compose file is the hardened configuration, not an example to harden later:

  • Non-root browsers. Playwright and the HTTP services drop to an unprivileged user; nothing that touches a web page runs as root.
  • no-new-privileges, memory and CPU limits, healthcheck — set in the shipped compose.yaml.
  • Pinned Playwright and browsers baked into the image at build time — the node never downloads browser binaries at runtime.
  • Hung runs are killed by a hard per-run timeout; the worker slot is freed and the service reports UNKNOWN rather than wedging the scheduler.

One honest caveat: Chromium runs with --no-sandbox inside the container, as is standard for containerized browsers, with privileges dropped instead. Point flows only at sites you trust and keep the image updated — this is listed in the residual-risk table below, not hidden.

Change control

Every change is gated, versioned and logged

  • Lint gate. The dashboard editor and the importer run the flow linter before anything is written — invalid YAML never lands on disk, with the linter's message shown to the author.
  • Version history with rollback. Every flow edit through the dashboard is kept as a revision; restoring the previous known-good version is one click.
  • Audit log. Who changed which flow, paused which check, triggered which run — recorded on the node and visible in the dashboard.
  • Pause/resume and tags. Maintenance window? Pause the check instead of deleting it. Tags group checks by team or application for filtering.
  • Script checks are operator-gated. Playwright Python checks only run from a directory the operator explicitly enables on the node. The dashboard cannot enable it; an author cannot smuggle code in through a flow. Disabled means disabled.

Capacity

Scale claims you can reproduce

Numbers from scripts/scale_test.sh in the repo — a 5-minute soak of 60 flows on a single container limited to 4 CPUs / 6 GB, every fifth flow a full multi-step login journey with secrets. Method and capacity formula: docs/scaling.md.

The overload contract: if you oversubscribe a node, the SynthMK Scheduler service goes WARN on the node, naming the overdue flows. Monitored applications never show false CRITs because the probe is saturated — the probe blames itself, by design.

Honesty section

What you still own as the operator

No vendor table ever lists these. SynthMK's are public, in the repo, with severity ratings. The short version:

SeverityResidual itemYour move
MediumChromium runs --no-sandbox in the container (standard for Docker; privileges dropped to an unprivileged user instead).Point flows only at trusted internal sites; rebuild the image on a schedule to pick up browser updates.
MediumClickable screenshot links need Checkmk's “Escape HTML codes in service output” set to Off — a known XSS surface if applied broadly (Checkmk Werk #6058).Scope that rule to the runner host(s) only. SynthMK emits a single sanitized line, but keep the rule narrow anyway.
LowThe lab/default agent transport (socat, port 6556) is plaintext.Use it only firewalled-to-the-Checkmk-server or in labs; switch production to the official TLS agent mode.
LowThe bundled lab ships hardcoded demo credentials for its demo site.Never reuse lab credentials outside the lab. They exist so the end-to-end test is reproducible.
LowSupply chain: the base image is pinned by version, not digest.Review MKP contents before distributing internally; pin by digest in your own build if policy requires it.
—Script checks, if you enable them, run with the node's privileges by definition.Treat the scripts directory like production code: review before deploy, restrict who can write to it.
